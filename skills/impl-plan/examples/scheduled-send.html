001 PostBox 작성 창의 예약 발송

사용자는 작성 창에서 보낼 시각을 고를 수 있다.

보내기 버튼은 그대로다.

「나중에 보내기」는 시각과 함께 저장만 하고 보내지 않는다.

한 사용자는 예약 메시지를 최대 50개까지 둘 수 있다.

사용자당 예약 메시지는 몇 개까지 둘까?

메시지는 정한 시각에만 나가고, 실패한 메시지는 남는다.

워커가 1분마다 시각이 된 메시지를 한 번만 가져간다.

실패한 발송은 다시 시도한 뒤 사용자에게 넘긴다.

실패한 발송을 저절로 다시 시도할까?

사용자는 예약 목록에서 메시지를 고치거나 취소한다.

워커가 잡기 전까지만 된다.

공유: 새 테이블 하나.

바뀌지 않는 것: 일반 발송, 임시 보관함, 메일 업체.

  • sendMessage()는 그대로 부른다.
  • 반복 발송은 없다. 메시지 하나에 시각 하나.

배경: 밤에 쓴 답장이 밤에 도착하지 않게 해 달라는 요청.

사용자 요청(원문): 「작성 창에 나중에 보내기를 넣어 달라. 취소할 수 있어야 하고, 절대 일찍 나가면 안 된다.」 고객지원 기록에도 밤에 답장을 쓰고 아침에 도착하길 바라는 사례가 반복된다.

지금 PostBox는 보내기를 누르면 바로 sendMessage()를 부른다. 보낼 시각을 저장할 곳이 없고, 정해진 시각에 메시지를 꺼내 보낼 프로세스도 없다.

  • 일찍 나가면 안 된다 — 발송은 send_at이 지난 행만 잡는다.
  • 워커가 둘 이상 떠도 같은 메시지를 두 번 보내면 안 된다.
  • 취소는 워커가 잡기 전까지만 이긴다. 늦으면 사용자에게 알린다.

  3. server/src/scheduled/routes.ts — 예약 생성·목록·수정·취소 라우트
  4. server/src/scheduled/store.ts — 테이블 접근(잡기·상태 변경)
  5. server/src/scheduled/worker.ts — 1분 주기 워커
  6. web/src/composer/SendLaterMenu.tsx — 「나중에 보내기」 메뉴
  7. web/src/scheduled/ScheduledFolder.tsx — 예약 목록

Affected Dependents: 바뀌지 않지만 계속 동작해야 하는 코드.

  • server/src/mail/send.ts sendMessage() — 워커가 그대로 부른다. 시그니처는 바뀌지 않는다.
  • server/src/drafts.ts saveDraft() — 취소된 예약이 임시 보관함으로 돌아갈 때 부른다.

Implementation Steps: 6단계.

  • Step 1: 마이그레이션

    File: migrations/0042_scheduled_messages.sql

    • scheduled_messages 스키마 그대로 테이블과 인덱스 scheduled_due를 만든다.

  • Step 2: 사용자당 개수 제한

    File: server/src/scheduled/limits.ts (새 파일)

    • 상한은 결정 limit의 값으로, 아래 상수 SCHEDULED_LIMIT 한 곳에만 쓴다. 다른 코드와 테스트는 이 상수를 가져다 쓴다. none이면 이 단계를 건너뛴다.
    // The decided per-user cap (decision `limit`).
export const SCHEDULED_LIMIT = 50

export async function assertUnderLimit(userId: string) {
  if (await store.countScheduled(userId) >= SCHEDULED_LIMIT) throw new LimitError(SCHEDULED_LIMIT)
}

  • Step 3: 예약 저장 라우트와 메뉴

    Files: server/src/scheduled/routes.ts, web/src/composer/SendLaterMenu.tsx, web/src/composer/Composer.tsx:41

    • POST /api/scheduled: 소유자와 상태는 세션에서 정한다. 요청 본문의 값은 쓰지 않는다.
    • Composer.tsx:41의 보내기 버튼 옆에 메뉴를 붙인다.
    export async function createScheduled(req: Request) {
  const session = requireSession(req)
  await assertUnderLimit(session.userId)
  const row = buildScheduled(await req.json(), session)
  await store.insert(row)
  return json({ id: row.id, sendAt: row.sendAt }, 201)
}

// Composer.tsx
<SendLaterMenu onPick={(at) => scheduleDraft(draft, at)} />

  • Step 4: 워커와 잡기

    Files: server/src/scheduled/worker.ts, server/src/scheduled/store.ts, server/src/app.ts

    • runScheduledSends()를 1분마다 돌린다. 잡은 행마다 sendMessage()를 부르고 결과에 따라 markSent·markFailed.
    • 잡기는 FOR UPDATE SKIP LOCKED로 — 두 워커가 같은 행을 잡지 않는다.
    UPDATE scheduled_messages SET status = 'sending'
WHERE id IN (
  SELECT id FROM scheduled_messages
  WHERE status = 'scheduled' AND send_at <= $1
  ORDER BY send_at LIMIT $2
  FOR UPDATE SKIP LOCKED
)
RETURNING *;

  • Step 5: 재시도

    Files: server/src/scheduled/worker.ts, server/src/scheduled/store.ts

    • 결정 retry가 3이면: attempts < 3이고 마지막 시도에서 5분이 지난 failed 행을 Step 4와 같은 방식으로 다시 잡는다. no면 이 단계를 건너뛴다.

  • Step 6: 예약 목록·수정·취소

    Files: server/src/scheduled/routes.ts, web/src/scheduled/ScheduledFolder.tsx

    • GET /api/scheduled: 이 사용자의 행만, send_at 오름차순.
    • 취소는 아래 조건부 갱신으로 — 돌아온 행이 없으면 이미 늦었다고 알린다.
    UPDATE scheduled_messages SET status = 'cancelled'
WHERE id = $1 AND user_id = $2 AND status IN ('scheduled', 'failed')
RETURNING id;

Tests: 서버 동작마다 하나.

  • should not claim a message before its send_at
  • should let only one of two workers claim the same row
  • should reject a scheduled message beyond SCHEDULED_LIMIT with 409 — SCHEDULED_LIMIT개를 채운 뒤 하나 더 저장한다(Step 2의 상수를 import).
  • should return no row when cancel lands after the claim

Risks: 시각대와 중복 발송.

  • 사용자 시각대를 잘못 바꾸면 일찍 나간다 — UTC로 저장하고 변환은 세션 시각대로 한 곳에서만 한다.
  • 워커가 보낸 뒤 markSent 전에 죽으면 다시 보낼 수 있다 — sending에 오래 머문 행은 자동 재시도하지 않고 사용자에게 넘긴다.

Verification: 테스트와 마이그레이션.
