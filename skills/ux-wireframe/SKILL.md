# UX 와이어프레임 (정리안 형식)

계약·설계 문서를 **기술 명세로 두고**, 운영자가 매일 보는 화면과 문구만 다시 짠 단일 HTML을 만든다.
계약표·상태 코드·버전 번호를 화면에 얹지 않는다. 화면은 「내가 이걸 누르면 무슨 일이 벌어지나」만 말한다.

## 산출물

파일 하나 `wireframe-<주제>.html`. 저장 위치는 사용자가 정한 곳, 없으면 프로젝트의 `docs/<영역>/` 아래이고 그것도 없으면 묻는다. 외부 자원 없음(폰트 링크도 없음). 구조는 `${CLAUDE_SKILL_DIR}/assets/skeleton.html`, 스타일은 `${CLAUDE_SKILL_DIR}/assets/base.css`를 **인라인**해 쓴다. 두 파일을 읽고 시작한다 — 상대경로는 프로젝트 루트로 풀리므로 반드시 이 형태로 읽는다.

## 언제 쓰지 않나

- 마케팅·랜딩 페이지, 발표 자료 → `design` / `artifact-design`
- 실제로 동작하는 프로토타입, 디자인 시스템·컴포넌트 산출물
- 화면이 아니라 코드 구조를 그리는 일 → `improve-codebase-architecture`

```
사이드바(= 위계도)  |  상단바(제목 · 요소 ID/주석 범례 · 데스크톱/모바일 토글)
                    |  s0  무엇을 바꿨나 — 요약 시트
                    |  s1… 화면마다: framelabel → frame(desktop[/mobile]) → notes(주석 + 조회/명령)
                    |  sN  빈 상태 · 오류
```

## 작업 순서

1. **근거를 읽는다.** 계약·상태·명령 문서에서 (a) 화면이 읽는 조회, (b) 화면이 보내는 명령, (c) 상태 축과 값, (d) 바꾸면 안 되는 것(코드값·정책)을 뽑는다. 이 넷은 화면 밖(주석의 `uses` 줄, 「바꾸지 않은 것」)에만 쓴다.
2. **원안을 진단한다.** 사람이 오해·실수하는 지점을 찾아 「가장 위험한 것부터」 번호를 매긴다. 각 항목은 *증상(사고 시나리오) → 원안/정리안 표 → 원칙 한 문장*. 이것이 s0의 본문이다.

   > **1. 「성공」이 성공이 아니다**
   > 증상 — 담당자가 초록 「성공」을 보고 창을 닫는다. 실제로는 3개 채널 중 1개만 나갔고, 나머지는 다음 날 문의로 돌아온다.
   > 원칙 — 접수와 결과는 다른 단어를 쓴다.
3. **위계를 정한다.** 사이드바 페이지는 매일 여는 것만(보통 3개 이하). 나머지는 그 아래 모달·drawer. 공용 모달은 최소로. s0에 위계도(`.ia`), 위계 규칙 표, 「어디서 무엇이 열리나」 표를 넣는다. 사이드바의 들여쓰기가 이 위계와 정확히 같아야 한다.
4. **화면을 그린다.** 페이지 → 모달 순. 각 화면은 요소 ID·번호 주석·notes를 갖춘다(아래 규칙).
5. **빈 상태·오류를 그린다.** 데이터 없음 / 필터 결과 없음 / 일시 오류 / 사용자가 못 고치는 오류.
6. **한 번 열어 본다.** 브라우저 도구가 있으면 스크린샷 한 장으로 *첫 화면이 렌더되는지, 사이드바 항목 수가 `T` 키 수와 같은지*만 확인하고 끝낸다(정적 캡처 한 장으로 화면 전환·토글은 확인되지 않는다). 도구가 없으면 건너뛴다. 어느 쪽이든 전환·토글·모바일 보기는 사용자에게 열어 보라고 알린다. 반복 렌더 루프 금지.

## 화면 규칙

- **요소 ID** `SC-<화면약어>-<3자리>`를 `.eid`로 붙인다. 화면 약어는 영문 대문자 3~5자. 빈 상태는 `SC-<약어>-E-<3자리>`, 오류는 `SC-X-<3자리>`(오류는 화면 공용이라 약어를 쓰지 않는다). 요구 목록·이슈에서 이 ID로 가리킨다.
  - `.eid.abs`(구역 우상단 고정)는 `position:relative`인 구역 안에서만 쓴다 — `.sec` `.banner` `.box` `.chcard`. 모달의 `.mh`/`.mb`/`.mf`에는 일반 `.eid`를 인라인으로 둔다.
- **번호 주석** `.co`(원 안 숫자)를 요소 옆에 두고, 그 화면의 `.notes ol`에서 같은 번호로 *결정 + 이유*를 쓴다. 이유는 「사용자가 무엇을 오해·실수하는가」다. 번호 없는 결정은 쓰지 않는다.
  > 예: `③ 버튼 문구를 「보냈습니다」로 바꿨습니다 — 「성공」이면 채널 하나가 실패해도 전부 갔다고 읽습니다.` `.notes li` 번호는 CSS 카운터로 매겨지므로, 화면에 나온 `.co` 숫자를 위에서부터 나열한 것이 `1,2,3…`과 정확히 같아야 한다 — `li`를 중간에 끼워 넣으면 뒤 번호가 통째로 밀린다.
- **notes 끝의 `.uses`** 는 항상 두 줄: `조회 — …` / `명령 — …`. 조회가 없으면 「없음(부모 화면 데이터)」, 명령이 없으면 「없음. 이동뿐」. 모달·빈 상태·오류 화면도 예외 없다.
- **첫 줄은 지시문.** 모달·배너의 첫 문장은 "지금 무엇이 나가는지 / 가서 무엇을 하라는지"다. 스냅샷·기술 정보는 그 아래 또는 「기술 정보 펼치기」 안.
- **원인은 결과보다 위.** 로그인 풀림 같은 원인 배너가 할 일 건수 배너보다 위에 온다.
- **되돌리기 어려운 동작은 2단계 확인**이고, 확인 화면은 문장이 아니라 *무엇이 어떻게 바뀌는지 표*로 보여준다.
- **선택지는 항상 보이고 불가한 것만 흐리게 + 이유.** 사라지면 "왜 없지"를 묻는다. 불가 버튼은 `.btn.off`(점선·회색).
- **처리 진입점은 하나.** 같은 일을 여러 화면에서 할 수 있으면 다른 화면에는 「○○에서 처리」 링크만.
- **모바일은 조회 전용**이 기본. 되돌리기 어려운 동작은 작은 화면에 두지 않는다. 모바일 프레임이 있는 화면만 `T[...][2]=true`.
- **파생·상태 필터 칩, 미선택 표시는 `.chip.dash`**로 구분한다(둘 다 「지금 켜져 있지 않다」는 뜻).

## 문구 규칙

- **축마다 품사를 가른다.** 같은 표에 두 축의 상태가 함께 나오면 한쪽은 명사(판매중·판매완료), 다른 쪽은 동사(올라감·내림)로. 두 글자 차이 라벨을 두 축에 두지 않는다. **코드값은 한 글자도 바꾸지 않는다.**
- **코드·버전 숫자·내부 용어는 화면에 없다.** 코드값이란 계약의 열거값·API·명령 이름·버전 번호다. 요소 ID(`SC-…`)와 주석 번호는 와이어프레임 표기라 예외다. 대신 실패 행마다 `[오류 정보 복사]`(코드·시각·요청 ID)를 두고, 상세는 「기술 정보 펼치기」에 넣는다.
- **접수 ≠ 성공을 단어로 해결한다.** "접수이지 성공이 아니다"를 반복해야 한다면 단어가 틀린 것이다(예: 「보냈습니다」 + 채널별 결과).
- **행동 기준으로 묶는다.** 계약의 축(작업·연결·계정)이 아니라 "사용자가 할 일"(로그인하기 / 다시 보내기 / 가서 확인하기)로 묶고, 순서에 인과를 담는다.
- **되돌릴 수 없는 선택은 선택지 안에 그 사실을 쓴다.** 모달 하단이 아니라 고르는 자리에.
- 빈 상태: 데이터 없음과 필터 결과 없음은 다른 문구. 「방금 보낸 것이 왜 안 보이는지」를 말한다.

## 스타일 규칙 (base.css)

- **무채색.** 강조는 테두리 두께·점선·채움으로만. 색은 `--accent` 하나이고 요소 ID·주석 번호·공용 표시(→)·사이드바 현재 위치에만 쓴다. 성공/실패를 색으로 구분하지 않는다.
- 상태 배지 `.st` 변형: `up`(정상·굵게) `none`(없음·점선) `block`(막힘·회색 채움) `down`(내림·흐림) `unk`(불명·굵은 점선) `na`(해당 없음). 새 상태가 생기면 이 여섯 중 의미가 같은 것에 매핑한다.
- 프레임·모달 폭은 base.css의 `.frame.desktop` / `.frame.mobile` / `.modal`(`.wide`) 정의를 그대로 따른다 — 숫자를 SKILL이나 화면 문구에 옮겨 적지 않는다. 모달은 `.dim` 위에 띄운다.
- 사진·이미지는 `.imgbox` 사선 패턴, 텍스트 자리는 `.bar` 막대. 실제 이미지 넣지 않는다. `.imgbox`는 높이가 없으므로 `.slots` 안에 두거나 높이를 직접 준다.
- 표는 `table.t`, 강조 행은 `tr.hi`. 숫자 열은 `.num`, 가운데 정렬 열은 `.chcol`.
- 페이지 구역은 `.sec`(8px 회색 띠로 구분), 하단 고정 바는 `.stickybar`(저장과 외부 전송 사이 `.divider`).

## s0 「무엇을 바꿨나」 시트 구성

1. 첫 문단: 원안의 장점 한 문장 → 핵심 진단 한 문장 → "아래 N가지".
2. 문제 N개: 제목(가장 위험한 것부터) · 증상 · 원안/정리안 표 · 원칙.
3. 화면 위계도(`.ia`) + 범례.
4. 위계 규칙 표(규칙 · 이유).
5. 「어디서 무엇이 열리나」 표(화면 · 종류 · 진입 경로 전부).
6. 원안 대비 화면 수 표(통합·삭제한 화면과 이유).
7. 「바꾸지 않은 것」 목록 — 명령·코드값·정책. 이 목록이 계약 대조의 기준이다.

## 하지 않는 것

- 화면 안에 계약표·필드 원천·상태 코드·버전 번호를 그리지 않는다. 필요하면 별도 md로 뺀다.
- 사이드바에 모달·참고 화면을 페이지와 같은 깊이로 나열하지 않는다.
- 모달 위에 모달을 쌓지 않는다. 바꿔 띄우고 끝나면 돌아온다.
- 실제 데이터를 쓰지 않는다. 예시는 그럴듯한 가짜 값이며 사용자 실데이터로 오인될 수 있는 이름·번호는 피한다.
- 산출물은 사용자가 읽는 문서이므로 **HTML·CSS 주석도 한국어**로 둔다(코드 주석 영어 규칙의 예외).

## 완료 체크

- [ ] 사이드바 들여쓰기 = s0 위계도 = 「어디서 무엇이 열리나」 표. 셋이 어긋나면 실패.
- [ ] 화면의 `.co` 숫자를 위에서부터 나열하면 `1,2,3…` 연속이고, `.notes ol`의 `li` 개수와 같다.
- [ ] 화면마다 `.uses`(조회/명령) 줄이 있다.
- [ ] **화면 안**(`.frame`·`.modal` 내부)에 계약 열거값·명령 이름·버전 번호가 보이지 않는다. 화면 밖인 `.notes`(`.uses` 포함)·s0 「바꾸지 않은 것」·「기술 정보 펼치기」·요소 ID는 해당 없음.
- [ ] 되돌리기 어려운 동작마다 2단계 확인 화면이 있고 표로 결과를 보여준다.
- [ ] 빈 상태·오류 화면이 있다.
- [ ] 사이드바 `data-s` = `section.screen` id = `T` 키. 셋이 정확히 같다.
- [ ] `{{…}}` 자리표시가 하나도 남지 않았다.
- [ ] `<style>`에 `${CLAUDE_SKILL_DIR}/assets/base.css` 전문이 인라인돼 있다(빈 style 아님).
- [ ] s0에 「무엇을 바꿨나」 7개 구성이 모두 있다.
